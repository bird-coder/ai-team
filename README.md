# ai-team

跨项目复用的 Codex 工作流。仓库保存角色、模型、流程和模板；业务代码、
需求、设计、计划、测试和报告全部保存在启动时选择的目标项目。

日常操作见 [USAGE.md](USAGE.md)：启动、两个入口、人工 review、批准、需求更新与恢复，均提供可复制指令。

## 启动

当前配置面向 Codex CLI 0.154.0。以此目录作为 CODEX_HOME，具体项目作为工作目录：

```bash
CODEX_HOME=/Users/jiajie.yu/go/src/ai-team \
  codex --strict-config --cd /Users/jiajie.yu/go/src/cas-game
```

也可使用启动脚本，自动定位 ai-team，并拒绝将自身或包含它的父目录作为业务项目：

```bash
bash /Users/jiajie.yu/go/src/ai-team/scripts/start \
  /Users/jiajie.yu/go/src/cas-game '实现任务：……'
```

路径替换为实际位置。只影响本次启动，不改变其他会话。无需复制角色到各项目。
项目已有 AGENTS.md 继续提供项目规则；没有时从项目文件识别约定，
可由你手动复制 templates/project-AGENTS.md 为新项目的 AGENTS.md，
填写占位内容；已有说明则手动合并，不能覆盖。也可以复制为游戏目录下的
project-rules.md 并在任务中指定，不要求创建项目根目录 AGENTS.md。

templates/ 仅供人工使用，由 Git 管理，不属于工作流指令来源。
工作流不会主动读取或应用其中的模板；仅在你明确要求查看、复制或维护模板时访问。
模板副本填写完成后，由项目 AGENTS.md 入口或任务显式指定的规则入口使用。

## 配置与职责

- config.toml：主会话 gpt-6-sol / high，与 orchestrator 角色保持一致；workspace-write，on-request 审批，
  最多 3 个并发子线程。
- AGENTS.md：此 CODEX_HOME 的全局入口，要求主会话负责调度。
- agents/*.toml：各子角色的模型、权限和职责。
- workflows/project-context.md：两工作流共用的项目规则、角色选择和委派约定。
- workflows/requirements-review.md：独立需求审核入口，完成后交接并停止。
- workflows/development.md：独立开发入口，核验并理解已审核需求后进行设计、实现与验收。
- skills/：ai-team-unit-tests（单元测试验收）、ai-team-developer-handoff（开发交接），
  以及固定版本的 ponytail-review（按需复杂度审查）。开发精简约束已并入开发交接技能。

| 角色 | 模型 | 推理强度 |
| --- | --- | --- |
| orchestrator、architect、product、reviewer、backend | gpt-6-sol | high |
| client | gpt-6-sol | medium |
| planner、qa | gpt-6-luna | medium |

主会话直接编排；orchestrator 子角色用于明确委派的独立工作流。
只读的 product、architect、reviewer 返回文档，由编排者写入目标项目。
实现角色写代码与测试，QA 独立验收，最多三轮自动返工。
技术栈和目录由项目提供，游戏场景仅在适用时检查。

这是配置与指令驱动的工作流，不是禁止其他行为的执行引擎。
项目指令、启动参数及运行时权限仍可能影响执行；角色/模型不可用时应报告，
不能悄悄替换。存在 orchestrator.toml 不会自动设置主会话模型。

## 开发阶段避免过度设计

backend/client 遵循现有开发交接技能中的精简约束，优先复用现有代码、
标准库和项目能力；无需另读 ponytail，也不为每次修改额外启动审查。
reviewer 遇到新增抽象、依赖、通用封装或明显重复代码时，按需读取 ponytail-review，
将复杂度建议与正确性审查分别记录，不替代独立审核，也不增加开发自查的重复循环。
其他角色不默认加载；未新增角色、全局插件或 hooks。

精简建议不能覆盖项目规则、已批准需求/设计、单元测试标准和交接要求。
不得为减少行数删去必要接口、测试或安全处理；重大简化先走人工 review。
减少行数不是验收目标，也不保证减少 token，实际收益需在项目中观察。
开发精简约束保留来源说明，ponytail-review 保留上游原文；来源、固定提交和许可证见 [skills/UPSTREAM.md](skills/UPSTREAM.md)。

## 项目选择开发角色

在任务指定的 project-rules.md 或项目 AGENTS.md 中填写一行即可，例如只开发后端：

```text
development_roles: [backend]
```

客户端/前端项目用 `[client]`，两端都开发用 `[backend, client]`。
这由工作流读取，不需要修改全局角色配置或删除 TOML 文件，也不是 Codex 原生配置键。
未填写时根据项目和任务识别，范围不清楚时才询问。

其他角色保持不变，单端项目仍完成需求评审、设计、计划、开发、Review 和 QA。
development_roles 只选择实现负责人，不限制只读设计咨询。涉及交互、跨端协议、
状态同步/重连时，编排者按需邀请对端角色参与设计评审；纯内部改动不固定调用。
咨询以 allowed_paths: [] 返回意见，由 architect 整合、编排者保存，不写对端代码或测试，
实现阶段指令不适用于只读咨询。未选端的实现不调用、不等待；咨询角色不可用时记录限制，
由 architect/reviewer 核对现有依据，不因角色缺失单独阻断，也不掩盖实际协议证据缺口。
若需求确实需要修改另一端，先明确范围或调整选择；选中的角色本身不可用、
需求未确认、测试缺少必要环境等真实问题仍会报告，不会伪造通过。
人工模板 templates/project-AGENTS.md 已包含三种选择示例。

## 项目业务规则与 skill

ai-team 管角色、模型、阶段和验收关口；具体项目的规则入口管项目约束与
业务 skill 入口，项目 skill 管相关文档的读取/维护方法，业务细节留在项目文档中。
不要把业务规则复制进 ai-team，也不需要在项目中重复定义八个角色。

项目可以在自己的 AGENTS.md 或显式指定的 project-rules.md 中写明：

```markdown
## 业务规则

- 涉及 <业务模块> 的任务，必须读取 .agents/skills/<业务技能>/SKILL.md，
  按其中导航读取 docs/<业务模块>/ 下相关文档。
- skill 中的开发、文档更新和测试步骤，只在当前角色权限与工作流阶段允许时执行。
- 需求、文档、代码存在业务或协议冲突时，报告差异并走对应评审，不自行改规则。
```

编排者将适用的项目指令、skill、业务文档及其版本作为 `project_rules` 传给
相关子代理；子代理执行前读取原文，交接时返回实际使用的来源和发现的冲突。
此字段是 ai-team 的任务交接约定，不是 Codex 配置键。不要求每个项目都有 skill，
也不要求每个角色读取全部业务模块。旧目录中的 skill 如被项目明确引用，可以
按指令路径读取，但不等于被自动发现；本工作流不会自行迁移或启用被禁用的 skill。

项目 skill 不扩大写权限、不跳过需求确认/协议评审，项目测试命令也不能替代
共享单元测试验收。单端项目仍阅读相关对端协议，但不因此启用另一开发角色。
文档维护沿用原有目录并指定写入负责人，只读角色把修改建议交给编排者保存。

### 不创建项目 AGENTS.md：按游戏指定规则入口

从 templates/project-AGENTS.md 人工复制并填写为 `docs/<游戏>/project-rules.md`。
文件名不固定，关键是在任务中明确选择。启动后输入例如：

```text
project_rules_file: docs/blackjack/project-rules.md
请按 ai-team 工作流评审 docs/blackjack/需求.md。
```

也可把这段任务说明作为 scripts/start 的第二个参数传入；不需要新增启动参数。
`project_rules_file` 是本工作流读取的任务约定，不是 Codex 配置键或原生加载开关。
规则入口及其声明的项目相对路径均以目标仓库根目录为基准，而非游戏文档目录。
规则文件可以配置 development_roles、业务 skill、文档、公共约束和验证命令。

编排者会记录入口路径、内容版本与游戏范围，并传给所有相关子代理；同一任务
恢复时沿用记录。切换游戏需显式指定新的入口并重新核对受影响的规则与审批。
指定文件不存在或无法读取时报告问题，不静默改用其他游戏规则。
未指定时继续使用适用 AGENTS.md 和现有项目约定，不自动创建文件。
显式入口不会屏蔽其他适用指令；触及公共模块时仍需读取公共规则，冲突须提出。

## 两个独立工作流

需求审核和开发分别启动，共享角色和项目规则，不重复编排。可自然语言指定，
也可在任务中写 `workflow: requirements-review` 或 `workflow: development`；
这是 ai-team 提示约定，不是 CLI 参数或 config.toml 配置项。

启动、问题回复、批准和恢复的可复制指令统一见 [USAGE.md](USAGE.md)。

只给原件或要求“审核后开发”，但尚无批准交接时，先走审核并在交接处停止。
需求确认本身不自动启动开发。已有基线的开发任务可直接指定开发入口；无效或
缺失证据先报告，不假定通过。恢复时沿用已记录的工作流，不因看到 READY_FOR_DESIGN 就进入开发。

### 需求审核

可以直接提供完整项目的需求文档，不需要策划先拆成功能或开发任务。
原始文档建议放在目标项目的 `docs/product/source/`；已有目录可以沿用，
启动任务时明确输入文件路径即可。完整项目使用一个项目级任务标识跟踪评审。

提供需求文档和目标项目后，先做“需求理解 → 业务拆分 → 逐项问答澄清”：
product 将歧义、缺漏和不合理之处挂在稳定需求编号下，你可以按编号直接回复，
也可以把问题交给策划修改；跨模块或全局问题单独保留并关联受影响需求。
architect 检查可行性，QA 检查验收条件。遇到问题不逐项卡住等待聊天回复，先完成
所有可安全独立开展的分析，将依赖未决问题的部分标为待定，集中输出 review.md。
交付文档后结束本轮，由你离线 review、按编号回复，再明确要求继续处理；不轮询等待。
补充内容全部标记为建议，不自动当作已确认规则，也不改写原始需求。

product 在评审阶段按“业务模块 → 用户场景 → 可验收需求”拆分完整需求，
用稳定编号关联原文、跨模块规则、业务依赖和验收条件，检查整份需求是否遗漏。
这不是技术架构或开发任务拆分；planner 在开发文档阶段依据 agent 评审通过的设计拆任务，
计划与设计一起交给你 review，而不是先写代码再补计划。
不能擅自裁剪成 MVP，也不能让局部清晰的模块绕过完整项目的需求准入。

评审产物默认在目标项目的 `docs/tasks/<task-id>/requirements/round-<n>/`：
理解说明、问题清单、可行性报告、验收条件建议、给策划的交接材料和准入记录。
完整项目另有 `decomposition.md` 保存业务拆分及原文覆盖关系；复杂模块才增加
同轮 `modules/` 明细，小需求可合并到理解说明中。拆分结果随每轮评审保存，
不另外维护一套重复的分析文档；已接受的拆分和验收条件纳入确认的需求版本。
每个需求项包含来源、理解、验收条件、依赖和问题链接；review.md 默认记录问题、
回复、决定及关闭依据。已有 issues.md 或条目记录时，只链接它们，不重复维护两份问答。
明确回复可补充或修正原件，
不必等策划更新原文件才生效；但逐项回复不等于已经批准整个项目进入设计。
review.md 是人工 review 和回复入口，handoff.md 引用它并提供给策划的交接摘要。
这里的策划是人类需求作者，与负责技术任务拆分的 planner agent 不同。

原件更新时重新读取并对照“上一版原件＋已记录回复”，保留编号和历史，按差异处理：

| 变化 | 处理 |
| --- | --- |
| 仅文案/排版变化 | 核对语义一致，记录版本映射，沿用有效结论 |
| 将已确认回复补入原文 | 核对一致并关联原决定，不重复提问 |
| 新增需求 | 新建编号，澄清并检查对已有需求的影响 |
| 修改或删除需求 | 保留历史，复核受影响需求、依赖及验收条件；不能自动将删除视为批准缩减范围 |
| 新原文与旧回复矛盾 | 列出双方依据，请你明确有效规则，不自动以最新文件覆盖决定 |
| 大幅改动或影响范围不明 | 必要时重新整体评估，仍保留可沿用的历史证据 |

round 是版本检查点，不是每条回复都重做全套文档。当前轮可追加问答；原件更新或
正式基线复评建立新轮，未变产物引用旧版本，不重复复制。已批准记录不得覆盖。

有未解决的阻塞问题就停在需求阶段，不编写业务代码或可执行测试。
澄清完成后仍由 product 检查整体一致性与覆盖，architect/QA 给出当前基线结论；
非阻塞风险需明确记录并由你接受。
即使评审没有问题，也要等你明确确认当前需求基线。
你的确认与工作流评估通过后，记录 READY_FOR_DESIGN，完成审核并停止，不进入设计或开发。
确认的基线由“原件版本＋已确认补充/修正决定＋拆分和验收条件”组成。
同一基线不重复询问；纯文案变化经等价核对记录后可沿用批准，语义变化则复核并
确认更新后的基线。开发中变化只暂停受影响工作，已证实独立的授权任务可继续。
具体约定见 workflows/requirements-review.md。

最终 handoff/gate 必须能在新会话独立使用：链接确切原件版本、理解/稳定需求编号、
实际问答决定、验收条件、范围/依赖、风险、评审结论及用户确认依据；不能只引用聊天消息编号。
复用已有文档和版本索引，不另写一套重复需求。

### 开发入口：重新理解，不重复完整审核

独立启动后，必须先调用 product 对照原件与审核产物，核对业务理解、覆盖、确认依据和风险。
architect 对照原文、已确认补充/修正和验收条件理解全部在开发范围内的需求，
在可冻结的设计章节中记录目标、边界和差异，开发状态只引用批准版本。不能只看到“审核通过”就开始写代码。
基线有效时不重复已解决的问答；发现新需求、冲突或缺失证据，反馈受影响编号，
进入用户指示的需求复核，保留独立任务进度。复核交接后由用户明确恢复开发。

需求审核拆的是业务模块/场景/行为；开发中的 planner 在 agent 设计评审通过后，对照原文、
审核产物和设计拆技术任务，明确负责人、依赖、路径、契约、验收与单元测试，并检查需求覆盖。
开发与审核可以使用不同 task-id，只要保存准确的上游交接引用；共用 task-id 时分开记录状态。

核验后 architect 定义模块/类型职责、公开接口、
协议字段与交互语义，reviewer 审查设计，QA 检查可测试性，记录 DESIGN_REVIEWED。
planner 据此输出开发计划和测试方案，reviewer 检查计划覆盖和依赖。
编排者将需求理解、架构、接口/协议、开发计划、测试方案及所有已知待决问题，
集中到 `docs/tasks/<task-id>/design/review.md`，交给你人工 review。
各文档可沿用项目目录或合并成有明确章节的文档，不为文件数量重复生成内容。
即使没有问题，也必须交付文档包等你批准；逐条回复不等于批准整个版本。
批准与 agent 检查都通过后才记录 DESIGN_APPROVED，由选中的开发角色落地
接口声明、协议源文件和必要骨架，完成生成/编译等检查，才进入
READY_FOR_IMPLEMENTATION，填充业务代码和单元测试。

协议有唯一源文件和修改负责人。实现阶段不得随意修改已确定的接口和协议；
变更需记录原因、兼容性和受影响任务，重大设计/契约/任务及测试计划变更须重新
提交受影响文档供人工 review，通过后更新版本并重新验证。
普通内部实现细节不反复要求人工确认；业务语义、重大架构和破坏兼容性的决定
沿用人工确认规则。单端项目同样遵循协议约定，不要求另一端开发角色存在。
具体规则及任务恢复方法见 workflows/design-review.md。

## 单元测试验收

行为变更代码必须有有效且通过的单元测试，缺失或失败不能验收。
backend/client 对自己实现的单元测试负责；planner 在任务中明确用例和命令，
reviewer 检查测试质量，QA 核对最终代码上的执行结果和需求覆盖。
测试记录默认写入目标项目的 docs/tasks/<task-id>/unit-tests.md。

测试要覆盖正常、边界和错误行为，修复缺陷要有回归用例。零测试、跳过必需用例、
只有构建成功或覆盖率数字，均不算通过。无法运行则记录 BLOCKED。
沿用项目测试工具和覆盖率要求，不统一强加 Go 命令或固定覆盖率百分比。
单端项目只验收所选端；必需的 Review、集成和业务验收仍然保留。
具体标准见 workflows/unit-test-acceptance.md。

该路径保留为兼容入口，要求继续读取 ai-team-unit-tests skill 及其完整标准。
标准正文与开发角色公共约定沿用已有抽取；模型、权限与单元测试验收标准不变。
开发准入以当前文档包人工 review 及后续契约检查为准。

## 与 BMAD 的对照和取舍

2026-09-14 对照 BMAD 官方文档后，保留现有八角色和模型配置，补充以下衔接规则。
这是对工作流方法的适配，没有安装 BMAD 或复制其技能实现。

| 对照点 | ai-team 原状 | 本次调整 |
| --- | --- | --- |
| 项目上下文 | 要求读项目，但未明确核实过期路径/命令 | 核实源码、构建和 CI 依据，只记录必要事实 |
| 开工准备 | 有设计关口，任务计划缺少整体检查 | Reviewer 检查需求覆盖、依赖、归属和决策完整性 |
| 任务交接 | 有任务格式，缺少统一状态语义 | 明确 READY、IN_REVIEW、IN_QA、DONE 等条件，由编排者维护 |
| 整体验收 | 已有 Review/QA，任务与整项完成区别不够明确 | 汇总后检查跨任务一致性和整项需求覆盖 |

## 运行数据

切换 CODEX_HOME 后，不要假定原来 ~/.codex 的配置、登录、MCP、插件和个人技能
会自动沿用。按需单独配置；本仓库不自动复制个人配置或凭据。
需要登录时，在同一 CODEX_HOME 下执行 codex login。
模型实际可用性仍取决于账号和提供方。

Codex 可能在此生成会话、日志、缓存和认证等运行数据。
.gitignore 用顶层源文件白名单将其排除在 Git 外；这是版本管理隔离，
不是物理隔离，也不阻止 git add -f。不要在受跟踪的配置里写凭据。
以后可用独立运行目录作为 CODEX_HOME，并安装或链接这里的配置源。
